# Правила сопровождения проекта «Светофор»

Рабочий репозиторий: `Stran22/svetofor22`. Рабочая ветка: `feature/excel-column-mapping`.

## Начало любого чата
1. Считать этот файл, `PROJECT_CONTEXT.md`, `docs/DATABASE.md`, `docs/API_ROUTES.md`, `docs/SERVER_CONFIG.md`, `docs/FEATURES.md` и `CHANGELOG.md`.
2. Проверить текущий HEAD ветки, конкретные исходники и миграции: документы описывают последнюю проверенную версию, но могут устаревать.
3. Не открывать новые ветки, не выполнять merge, rebase, reset, деплой или изменения в production без прямой просьбы.
4. Сохранять действующий дизайн и работу Android, PHP API, авторизации VK, отзывов, подписок и FCM. Не делать существующие функции заново.
5. Перед правкой проверить связанную цепочку БД → контроллер → API → Kotlin DTO/Retrofit → Compose → тесты.

## Постоянные продуктовые правила
- Каталог без корзины/оплаты; цены и остатки по магазинам.
- «Следить за товаром»: **одна подписка на товар**, не на филиал. Кнопка только когда у **каждого активного филиала** есть запись stock и quantity строго 0. Проверяется через `ApiController::product` (`can_track`) и повторно через `SubscriptionController::create`. Подписка только после авторизации (не guest).
- Скрытие блока «Цены и остатки в магазинах» управляется `categories.hide_store_stock`, наследуется от родителя категории, редактируется через `/admin/categories/visibility`. Учитывать при Android-рендеринге.
- Импорт XLSX по одному филиалу, до 5 МБ, с предпросмотром и сохранённым сопоставлением колонок.

## Правило изменения документации
При каждом важном изменении **в том же коммите**:
- Изменение БД → `docs/DATABASE.md`.
- Новый/изменённый маршрут или контракт → `docs/API_ROUTES.md`.
- Изменение состояния возможности → `docs/FEATURES.md`.
- Причины, файлы, проверки → `CHANGELOG.md`.
- Текущая задача, проверки, известные проблемы, следующий шаг → `PROJECT_CONTEXT.md`.
- Изменение окружения → `docs/SERVER_CONFIG.md`.
Не записывать пароли, токены, приватные ключи, `google-services.json`.

## Правила безопасности и качества
Не выполнять боевые миграции автоматически: `007_product_wide_subscriptions.sql` содержит `DELETE FROM subscriptions`. До миграции нужна проверка `schema_migrations`, резервная копия и явное согласование. Не запускать `--send` для push без согласования. Тесты: `composer lint`, `composer test`, MySQL integration и Android Gradle (где применимо). Если не запускались — так и писать.
Исторические `docs/api-contract.md`, `docs/architecture.md`, `android/README.md` могут описывать старые OneSignal/подписку по филиалу/незарегистрированные endpoints. Действующий исходник и миграции приоритетнее.
