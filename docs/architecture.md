# Svet22 — архитектура проекта

## 1. Назначение и границы

Svet22 — информационный каталог продуктового магазина для двух филиалов в Бийске. Покупатель видит единый каталог, но цену и остаток отдельно по каждому филиалу. Корзины, заказа, оплаты и функции покупки нет.

Основные сценарии:
- просмотр категорий и товаров;
- поиск, фильтрация и сортировка;
- карточка товара с ценой/остатком в обоих филиалах и историей цен;
- подписка на отсутствующий товар в конкретном филиале;
- push после появления товара;
- отзывы и рейтинг только от пользователей, вошедших через социальный аккаунт;
- гостевой просмотр каталога, отзывов и push-подписок.

## 2. Технологические решения

### Backend
- PHP 8.5.12 на Apache, MySQL 8.0.46, PDO.
- Чистый PHP без Laravel/Symfony и других тяжёлых фреймворков.
- Composer + PSR-4; PhpSpreadsheet для XLSX; cURL для OneSignal и OAuth HTTP-вызовов.
- REST API с JSON; админ-панель использует PHP Sessions + CSRF.
- Android API использует Bearer-токены: в БД хранится только SHA-256-хэш.
- Секреты и параметры окружения находятся в конфигурации вне `public_html`.
- CLI-задачи запускаются только через `/opt/php85/bin/php`, проверяют SAPI, используют lock-файл и лог.

### Android
- Kotlin, Jetpack Compose, Material 3, MVVM, Hilt, Retrofit/OkHttp, Room (только кэш), Coroutines/Flow, Navigation Compose.
- Application ID: `ru.altajotdyh.svetofor2`.
- JDK 17; версия SDK и библиотек фиксируется в version catalog.
- Приняты конкретные версии из дополнения к заданию: Gradle 8.7, AGP 8.6.1, Kotlin 2.0.21, compile/target SDK 34, min SDK 24. Это осознанно разрешает противоречие с первоначальным minSdk 26; перед релизом SDK-уровни можно изменить отдельным согласованием.
- OneSignal получает `external_id = users.id` после регистрации устройства/входа.

## 4. Модель данных

Полная первая миграция находится в `database/migrations/001_initial_schema.sql`.

Ключевые правила:
1. `products` — единый справочник товара, не зависящий от филиала.
2. `stock` — ровно одна текущая запись на пару товар + филиал.
3. `price_history` — история по паре товар + филиал; уникальность товар + филиал + дата защищает от дублей за день.
4. `subscriptions` — подписка на конкретный товар в конкретном филиале.
5. Гостевые и социальные пользователи представлены одной таблицей `users`; социальные идентификаторы вынесены в `social_accounts`.
6. OAuth state и одноразовые handoff-коды хранятся в виде хэшей и имеют срок действия.
7. `upload_log` и `import_errors` сохраняют результат каждой загрузки и ошибки отдельных строк.

## 5. Правила сопоставления товара при импорте

Порядок:
1. Если есть артикул и производитель — поиск по паре `manufacturer + article`.
2. Если по артикулу товар не найден — поиск по штрихкоду.
3. Если артикул и штрихкод указывают на разные существующие товары — строка отклоняется как конфликт идентификаторов, автоматическое объединение запрещено.
4. Если совпадений нет — создаётся новый товар.
5. Категория ищется по названию; при отсутствии создаётся. Категории с одинаковым названием в разных родительских ветках независимы.
6. Цена и остаток обновляются только у выбранного филиала.

Штрихкод и артикул обрабатываются как строки, чтобы не терять ведущие нули. Не следует жёстко ограничивать длину штрихкода конкретным стандартом: в приложенном примере есть тестовые значения разной длины.

## 6. История и разница цен

История хранит только первую известную цену и фактические изменения, а не бессмысленный ежедневный повтор одинаковой цены.

При импорте за дату D:
- если записи за D ещё нет и цена отличается от текущей цены до импорта — добавить запись за D;
- если запись за D уже есть — обновить её через UPSERT, не создавая дубль;
- если цена не менялась — новую запись не добавлять;
- текущая цена в `stock` обновляется независимо от истории.

Для API:
- `previous_price` — последняя известная цена с датой строго меньше даты текущего импорта;
- `price_diff = current_price - previous_price`;
- `price_diff_percent = (price_diff / previous_price) * 100`, если previous_price больше нуля;
- положительная разница означает подорожание, отрицательная — снижение;
- если предыдущей цены нет, diff возвращается как null.

При нескольких импортных запусках за один день уникальный ключ `product_id + branch_id + recorded_date` не допускает дублей. Для точного внутридневного аудита изменений потребуется отдельное согласование — текущая модель показывает дневную историю.

## 7. Push-уведомления

Подписка относится к конкретному филиалу. Cron-задача выполняется раз в час:
1. Берёт активные подписки, у которых `notified_at IS NULL`.
2. Проверяет актуальный `stock.quantity > 0` для той же пары товар + филиал.
3. Отправляет уведомление в OneSignal с `include_aliases.external_id = [users.id]`.
4. Только после подтверждённого успешного ответа OneSignal записывает `notified_at` и переводит подписку в notified.
5. При ошибке отправки оставляет подписку активной для следующей попытки, записывает ошибку в лог; ограничивает число повторов/период, чтобы не создавать бесконечный поток запросов.
6. Перед отправкой повторно проверяет статус подписки и остаток; блокировка/атомарное резервирование не позволяет двум процессам отправить одно уведомление.

Повторное уведомление возможно только после явного повторного включения подписки пользователем (сброс `notified_at`).

## 8. Импорт XLSX

- Импорт запускается только вручную из админки.
- Перед загрузкой администратор выбирает филиал.
- Файл сохраняется во временный каталог вне `public_html`, проверяются размер, расширение, MIME и заголовки.
- Парсер читает строки, валидирует каждую независимо.
- Валидные строки обрабатываются в транзакции; если критическая ошибка БД прерывает транзакцию, импорт помечается failed.
- Ошибки отдельных строк пишутся в `import_errors`, остальные корректные строки продолжают обрабатываться.
- После завершения файл удаляется.
- Повторная загрузка того же файла за ту же дату не дублирует товары и историю цен.

## 9. Порядок разработки

1. Этап 1 — архитектура, SQL, API-контракт и формат XLSX.
2. Этап 2 — backend core, авторизация и API.
3. Этап 3 — импорт, история цен и push cron.
4. Этап 4 — админ-панель.
5. Этап 5 — Android-каркас и экраны.
6. Этап 6 — интеграционные проверки и инструкция деплоя.

Backend и его тесты стабилизируются до начала Android-интеграции. Production-развёртывание и слияние PR выполняются только после отдельного согласования.
