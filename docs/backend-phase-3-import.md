# Этап 3 — импорт XLSX

## Реализация
- `XlsxImportService` принимает путь к временному файлу, исходное имя, выбранный администратором филиал и необязательную дату снимка.
- Поддерживается XLSX до 5 МБ; проверяются расширение, доступность файла и MIME.
- Заголовки сопоставляются по названиям, порядок колонок не важен; обязательны «Название», «Цена», «Остаток».
- Штрихкод и артикул сохраняются как строки. Для чтения штрихкодов в XLSX рекомендуется задавать текстовый формат ячеек.
- «Производитель» сохраняется без переосмысления значения.
- Пустые строки пропускаются, ошибочные строки регистрируются в `import_errors`; валидные строки обрабатываются в одной транзакции.
- Категория создаётся при отсутствии.
- Товар сопоставляется по паре артикул + производитель, затем по штрихкоду. Конфликт идентификаторов отклоняет строку.
- Цена/остаток относятся только к выбранному филиалу.
- UPDATE выполняется только при фактическом изменении данных. История цен создаётся при первой цене и пополняется только при изменении цены; изменение одного остатка не меняет историю.
- Повтор того же файла для филиала и даты возвращает ранее завершённую загрузку.

## Ограничения этого этапа
- Это сервисный слой импорта, а не готовая административная форма или HTTP upload endpoint. Экран выбора филиала, проверка сессии/CSRF и безопасное сохранение временного файла входят в этап админ-панели.
- В CI поднимается MySQL 8.0, применяется начальная миграция и выполняются интеграционные проверки импорта: первичная загрузка, повтор того же файла, изменение только остатка, изменение цены, разделение остатков по филиалам и продолжение обработки после ошибочной строки.
- Файл не меняет остатки товаров, отсутствующих в выгрузке.

## Проверка
Запуск: `composer test`. Если переменные `SVET_TEST_DB_*` не заданы, MySQL-интеграционные проверки пропускаются; в GitHub Actions они запускаются с отдельной тестовой MySQL 8.0.
